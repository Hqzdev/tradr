# TRADR backend — обзор и вердикт

## Вердикт

Сейчас у тебя есть Next.js-макет: ~30 экранов, красивая дизайн-система,
и **ноль настоящей логики**. Всё, что выглядит как продукт — цены, свечи,
поведение агентов, P&L, состав портфеля — это захардкоженные фикстуры в
`apps/web/lib/*.ts`. `useTicker.ts` не тикает рынок, а крутит один и тот же
массив из 10 чисел по кругу. Агенты не принимают решений — их "решения"
это строки текста, вписанные руками. Это нормально для дизайн-макета и
плохая новость, если ты хочешь называть это MVP: ты выбрал **закрыть все
экраны сразу**, а не тонкий сквозной срез — то есть тебе нужен не один
бэкенд-модуль, а семь: auth, рыночные данные, ордера/сделки/портфель,
движок агентов, симуляции, команды, настройки. Это не "бэкенд на выходные".

Дальше в этом документе — честная оценка объёма по фазам (`04-roadmap.md`),
и ты либо принимаешь это как есть, либо режешь scope сейчас, а не через
месяц, когда упрёшься в четвёртую фазу и надоест.

Отдельная дыра: **сейчас в коде нет ни одного экрана логина/регистрации** —
в README упомянуты "вход, регистрация" как часть макета в `design.pen`, но
в `apps/web/app` их нет вообще. Multi-user продукт без auth не существует —
это Phase 1, раньше рынка и агентов.

## Стек

- **Java 21 + Spring Boot 3** — Web (REST), Security (JWT), Data JPA, Validation, WebSocket
- **PostgreSQL 16** — основное хранилище, включая time-series свечи (без отдельной
  time-series БД на старте — партиционирование по инструменту/таймфрейму, если
  объём данных начнёт мешать, это отдельная задача не для MVP)
- **Flyway** — миграции схемы, обязательны с первого коммита
- **Docker** — единственный способ деплоя (см. "Инфраструктура" ниже)
- **Testcontainers** — интеграционные тесты против настоящего Postgres, не H2

## Архитектура (коротко)

Слоистая монолит-архитектура, один Spring Boot процесс на старте (никакого
микросервисного распила — тебе это не нужно на этом масштабе и только
замедлит разработку):

```
Controller → Service → Repository (JPA) → Postgres
                ↓
        WebSocket broadcaster (котировки, живые решения агентов,
        обновления симуляции — всё, что должно приходить пушем,
        а не по polling)
                ↓
        Scheduled tick engine (двигает рынок и агентов по таймеру,
        см. 03-market-data-and-agents-engine.md)
```

Auth — JWT (access + refresh), Spring Security фильтр-цепочка, пароли —
BCrypt. Никакого session-based auth: фронт на Vercel и бэкенд — разные
домены, куки между ними — лишняя головная боль.

## Инфраструктура — важная поправка

Ты сказал "будет Vercel, но докер да, только у меня OrbStack". Это две
разные вещи, и их надо разделить сейчас, а не когда дойдёшь до деплоя:

- **Vercel хостит только фронтенд** (Next.js). Он не запускает произвольные
  долгоживущие JVM-процессы, не держит постоянное соединение с Postgres и
  не умеет long-lived WebSocket-соединения, которые нужны движку агентов и
  живым котировкам. Разворачивать Spring Boot на Vercel — тупик, даже не
  пытайся.
- **OrbStack** — это локальная замена Docker Desktop на macOS, он говорит
  по тому же Docker CLI/daemon протоколу. Годится для локальной разработки
  (`docker compose` в этой папке уже на нём и рассчитан), но это не хостинг
  для продакшена — это то, что работает только пока открыт твой ноутбук.
- **Для продакшена бэкенда** нужен отдельный хостинг, который запускает
  Docker-контейнер и даёт managed Postgres: Railway или Render — ближе всего
  по опыту к Vercel (git push → деплой), Fly.io — если понадобится больше
  контроля над WebSocket/регионами. Держи `Dockerfile` в `backend/` с первого
  дня, чтобы это решение можно было принять поздно и без переписывания кода.
- Итоговая схема: **фронт на Vercel** → HTTPS/WSS → **бэкенд в контейнере на
  Railway/Render/VPS** → **Postgres** (managed или в том же контейнерном
  окружении). CORS на бэкенде должен явно разрешать домен Vercel
  (`CORS_ALLOWED_ORIGINS` в `.env`).

## Источник рыночных данных

Ты не знаешь, нужен ли внешний API, и просил: если легко — используем.
Ответ: **не блокируй MVP на внешнем API**. Строй `MarketDataProvider` как
интерфейс с двумя реализациями с первого дня — `SyntheticMarketDataProvider`
(детерминированный генератор, портирует логику `useTicker.ts`/`fixtures.ts`
на сервер) и `FinnhubMarketDataProvider` (реальные данные). Начинаешь с
synthetic — это ноль внешних зависимостей и ноль риска rate-limit'ов, а
переключение на Finnhub — это Phase 8, отдельная и необязательная для
"продукт работает" веха. Подробности и сравнение провайдеров —
`03-market-data-and-agents-engine.md`.
