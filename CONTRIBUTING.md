# Участие в TRADR

Спасибо за улучшения проекта. Исходный код и Pull Request находятся в [github.com/Hqzdev/tradr](https://github.com/Hqzdev/tradr). Перед началом работы ознакомьтесь с [локальным запуском](./DEVELOPMENT.md) и архитектурными границами в [ARCHITECTURE.md](./ARCHITECTURE.md).

## Перед изменением

1. Сформулируйте цель и затронутую предметную область.
2. Проверьте, нет ли незавершённых изменений в тех же файлах.
3. Для заметной функции или изменения контракта сначала согласуйте короткий план.
4. Не добавляйте секреты, пользовательские данные и файлы окружения в Git.

## Ветки

- `main` — стабильные релизные изменения. Прямой push запрещён.
- `develop` — общая ветка интеграции. Новая работа начинается от неё.
- `feature/<краткое-имя>` — новая возможность, например `feature/custom-agent-profile`.
- `fix/<краткое-имя>` — исправление ошибки, например `fix/dashboard-empty-state`.
- `docs/<краткое-имя>` и `chore/<краткое-имя>` — документация или служебная работа.

Одна ветка — одна задача. Не смешивайте в ней рефакторинг, новую функцию и правку текста. После слияния ветку удаляют.

```bash
git switch develop
git pull --ff-only origin develop
git switch -c feature/short-task-name
```

## Коммиты

Коммит описывает одно завершённое изменение. Используйте формат `тип(область): действие`:

```text
feat(agents): add custom profile validation
fix(market): preserve quote timestamp on fallback
docs(git): describe pull request workflow
chore(web): update release notes
```

Допустимые типы: `feat`, `fix`, `docs`, `refactor`, `test`, `chore`. Не используйте сообщения вроде `fix`, `changes` или `wip` в готовой истории.

## Pull Request

Pull Request открывается из рабочей ветки в `develop`. В `main` попадают только проверенные изменения из `develop`.

В описании PR укажите:

- цель и результат для пользователя или системы;
- затронутые файлы и контракты API, если они менялись;
- выполненные тесты и ручную проверку;
- скриншот или короткую запись для заметного изменения интерфейса;
- известные ограничения и отдельные задачи, если они остались.

Перед открытием PR выполните `git diff --check`, синхронизируйте ветку с `develop` и убедитесь, что секреты не попали в diff.

```bash
git add <файлы>
git commit -m "feat(scope): short action"
git push -u origin feature/short-task-name
```

## Принципы кода

- Один класс — одна ответственность.
- Инкапсулируйте состояние и правила предметной области.
- Предпочитайте композицию наследованию.
- Не оставляйте мёртвый код, временные заглушки и неиспользуемые зависимости.
- Не смешивайте DTO, HTTP-логику и бизнес-правила.

## Проверка

Перед передачей изменений выполните проверку, которая соответствует затронутому слою:

```bash
npm run test:web
npm run test:backend
```

Если изменение влияет на оба приложения, запустите также полный локальный контур через `npm run dev` и проверьте `/health`.

## Описание изменения

В описании укажите:

- что изменилось для пользователя или системы;
- какие модули затронуты;
- как это проверено;
- какие ограничения или последующие шаги остаются.
