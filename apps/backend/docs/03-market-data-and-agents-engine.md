# Рыночные данные и движок агентов

## Источник цен — абстракция с первого дня

Интерфейс (набросок сигнатур, не готовый Java-код — пишешь сам):

```
interface MarketDataProvider {
    Quote getQuote(String ticker);
    List<Candle> getCandles(String ticker, Timeframe tf, int limit);
    Flux/Stream<Tick> streamTicks(String ticker); // или callback-подписка
}
```

Две реализации:

1. **SyntheticMarketDataProvider** — детерминированный генератор,
   портирует логику `apps/web/lib/fixtures.ts: buildCandles()` /
   `apps/web/lib/useTicker.ts: SCENARIO` на сервер. Стартуй с этого. Ноль
   внешних зависимостей, ноль rate-limit'ов, поведение идентично тому,
   что уже видел на фронте — упрощает сравнение "бэкенд считает то же,
   что раньше рисовал фронт".
2. **FinnhubMarketDataProvider** — реальные данные. Сравнение вариантов
   (актуально на момент подготовки плана, проверяй лимиты и условия перед
   интеграцией — тарифы меняются):
   - **Finnhub** — рекомендация. Free tier: 60 запросов/мин, реальные
     котировки и сделки по US-акциям, бесплатный WebSocket-поток тиков,
     дневные свечи на десятилетия назад. Условие: free tier — только
     non-commercial/personal use, для монетизированного продукта придётся
     переходить на платный план.
   - Twelve Data — free tier 8 credits/мин, 800/день, есть внутридневные
     свечи (1м/5м/15м/1ч), но полноценного бесплатного WebSocket по факту нет
     (только урезанный trial).
   - Alpha Vantage — free tier 25 запросов/день. Для чего-либо кроме
     разового теста непригоден.
   - Polygon.io — с 2026 переименован в Massive.com, free tier — только
     EOD-данные, без WebSocket, 5 запросов/мин.
   - IEX Cloud — сервис закрыт, не рассматривать.
   - Fallback, если даже Finnhub начнёт мешать лимитами или условиями
     использования: остаться на synthetic provider постоянно, либо
     подмешивать synthetic поверх последней реальной котировки (random-walk
     вокруг последней цены от Finnhub), чтобы не упираться в лимит на
     каждый тик.

`MARKET_DATA_PROVIDER` в `.env` и `PUT /settings/data` на уровне
пользователя переключают реализацию без изменения кода вызывающей стороны
(движок агентов и REST/WS-слой работают с интерфейсом, им всё равно, откуда
данные).

## Тик-движок (scheduled)

Один `@Scheduled`-компонент (или отдельный поток с фиксированным
интервалом — не обязательно Spring `@Scheduled`, но проще для MVP), тикает
каждые N секунд (в макете — 2.6с на тик, `useTicker.ts: intervalMs`,
разумный дефолт):

1. Для каждого активного инструмента — получить следующую цену через
   `MarketDataProvider`, записать/обновить текущую свечу, широковещательно
   отправить в `/ws/market/{ticker}`.
2. Для каждого активного `Agent` (live-режим, не внутри симуляции) — вызвать
   `Strategy.decide(marketState, agentConfig)` → `Decision(action, reason, rules)`.
3. Если `action != wait` — создать `Order`, исполнить мгновенно по текущей
   цене (переиспользуя ту же логику расчёта, что в `POST /orders/preview`),
   создать `Trade`, обновить `Position`, записать `AgentDecisionLog`,
   отправить событие в `/ws/agents/activity` (и, если агент состоит в
   команде — попадает в ленту команды тем же событием).
4. Если `action == wait` — тоже пишется в `AgentDecisionLog` (в макете видно
   "Ждёт сигнал" как валидное решение, это не отсутствие данных, а осознанный
   выбор агента).

## Стратегии — три встроенные + путь к кастомным

`Strategy` — интерфейс с одним методом `decide(...)`. Три реализации на
старте, по смыслу из `fixtures.ts: agents` и `agentsData.ts: agentDetails`:

- **AggressiveStrategy** — входит чаще, большим объёмом, короткий порог
  подтверждения сигнала (в макете: импульс цены + рост объёма → buy).
- **CarefulStrategy** — ждёт более сильного подтверждённого сигнала,
  меньший объём на сделку, есть стоп-лосс правило.
- **RandomStrategy** — контрольная группа, решение не зависит от рыночного
  состояния (псевдослучайно, но с фиксированным seed на симуляцию, чтобы
  результаты симуляции были воспроизводимы при повторном запуске с тем же
  seed — это важно для доверия к бэктесту).

Каждое решение отдаёт `rules: [{label, ok}]` — ровно то, что уже
показывается в `AgentDetailScreen.tsx` (блок с чек-листом правил). Строй
стратегию так, чтобы `rules` были естественным побочным продуктом
вычисления решения, а не текстом, придуманным отдельно от логики — иначе
экран будет врать о том, почему агент решил то, что решил.

"Кастомный" агент (если дойдёшь до этого — экран `AgentSetupTypeScreen`
подразумевает несколько типов создания) — тот же интерфейс `Strategy`, но
пороги (какой % импульса, какой объём в сделке) берутся из
`AgentConfig.character` / `.budget` / `.skills` вместо хардкода. Не
проектируй DSL или плагинную систему для этого — это over-engineering на
этом этапе; параметризованная реализация тех же трёх стратегий достаточна
для MVP.

## Симуляция (backtest) vs live — одна и та же Strategy

`Strategy.decide()` не должен знать, идут ли данные с живого рынка или из
`SimulationDataset`. Реализуй это через общий интерфейс "источник рыночного
состояния на шаге N" — для live это текущий тик, для backtest это i-я
свеча датасета, проигрываемая с настраиваемой скоростью (`Simulation.config.speed`).
Если стратегия жёстко завязана на реальное время (`Instant.now()`), backtest
будет либо невозможен, либо будет врать — прогоняй тесты стратегии именно
через backtest-путь, это дешевле, чем гонять live.
